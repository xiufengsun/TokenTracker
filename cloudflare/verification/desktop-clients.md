# Desktop client verification, 24 November 2026

**macOS.** The arm64 Release build used the bundled Node 22.22.2. Chrome 158 logged into the Cloudflare QA Worker through that server, displayed the expected account ID after a reload, approved a CLI device, signed out, and kept the next visit signed out. The browser recorded zero InsForge requests. A controlled Codex log produced 7,331 tokens. The real CLI drained its queue to EOF and the Cloudflare account report for the issued device returned 7,331. This covered the embedded HTTP server and the built frontend.

**Windows.** Microsoft’s official .NET 8.0.428 macOS arm64 SDK was SHA-512 verified before use. Cross-publishing the repository's Windows project with Release, win-x64, self-contained and EnableWindowsTargeting produced TokenTracker.exe, WebView2Loader and the Windows desktop runtime 8.0.34. Each checked native PE file identified as x86-64. The locally assembled verification directory included the official checksum-verified Windows Node 22.22.2, all 132 current CLI source files with matching bytes, and the built index, quota and pet HTML entries. The 171 cross-platform .NET tests passed. Windows-native launch, WebView2 interactions, URL protocol dispatch and the Inno installer remain unverified on this machine.

**Linux.** No installed x86-64 Linux guest or local container runtime was available on the arm64 Mac. A temporary Rust harness exercised the project's callback parsing, runtime path resolution, desktop entry, background sync and CLI arguments on Darwin. The 27 tests passed. The harness used the same URL crate version as Tauri, without launching GTK/WebKit. The shared Linux bundling and Windows/Linux release-workflow test files also passed all 46 tests. The Linux bundler test uses a fixture Node binary. AppImage, DEB, RPM installation and native desktop login remain unverified for this revision.

**macOS native social login.** On 24 November the isolated TokenTrackerQA app opened Google and GitHub in the system default Chrome browser. Both returned through the registered QA URL scheme to AppKit. The original WebKit page exchanged the code with its PKCE verifier against the Cloudflare QA deployment, received HTTP 200, displayed the expected original QA user ID in Settings, signed out with HTTP 200, then reloaded into a signed-out page. Each provider ran in a separate ephemeral WebKit session. The QA target uses the dedicated QA bundle, loopback port and callback scheme `tokentracker-qa://auth/callback`; the shipping bundle uses `tokentracker://auth/callback`. The check covered the native application and system URL dispatch with QA credentials. Production OAuth credentials and callbacks require their own acceptance at cutover.

For a repeat run, build the TokenTrackerNativeQA scheme, copy the QA app into a private directory recognized by LaunchServices and ad-hoc sign it. Pass the provider, that app bundle path and the operator-owned QA file containing TT_QA_ID to cloudflare/worker/test/device-native-oauth-preview.mjs. The runner accepts the existing account ID only as proof of the expected result. It creates an ephemeral web view, a private temporary home and a loopback server restricted to authentication. After both runs, unregister and remove the disposable copy. The production URL handler must still resolve to the installed app.

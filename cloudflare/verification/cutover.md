# TokenTracker 后端切换顺序

本次范围为 TokenTracker 云后端。Cloudflare 负责当前权威 DNS，阿里云仍为注册商，网页部署在 Vercel。InsForge 数据库还供 AgentMeter 使用，停写必须按应用隔离。

1. 在同一 PostgreSQL 快照上导出 TokenTracker 业务关系与身份投影，保存 GPG 文件和外部可恢复的密钥。记录源快照、业务表/序列、函数代码和定时任务清单。正式导出时使用正式身份映射密钥，QA 密钥仅用于演练。
2. 在独立目标库恢复数据。复制源账号 UUID、原 provider subject、金额、设备令牌哈希及每条记录的时间，核对完整性、行数和分型摘要。单独核对归档表、缓存和重算的派生表，记录关闭源库后仍需离线查询的历史表。全量库在检查前保持无公网绑定。
3. 给待发布版本配置自有 API 地址，并明确公开配置与实例归属。Web、npm 和三个桌面分发包按正常更新链路验收。生产切换窗口必须启用 [登录连续性桥接](./auth-continuity.md)，让旧 access/refresh session 先换发 Cloudflare session。历史已安装版本使用 InsForge 的第三方主机名；供应商关服后，这些地址能否继续工作取决于供应商是否提供转发。以实际版本分布和上传数据决定旧入口保留期。
4. 对真实部署域名跑自有 GitHub、Google、邮箱回调和设备授权，按账号比对 private summary、排行榜与付费权益。QA 的 OAuth 回调地址会随生产域名改变。生产 Worker 的调度和 Waffo 商户生产回调均需在同一切换窗口交接。
5. 在 InsForge 端阻止 TokenTracker 的新写入。覆盖设备上传、令牌签发、账号编辑、Waffo 事件、设备清理、管理员写入与调度。Webhook 要返回可重试的状态或先持久记录事件，不能在未落账时确认收件。为已批准且仍有效的旧设备码保留完整的到期窗口，或在目标启用签发前失效化。用真实只读观察确认 TokenTracker 写入停止，单靠网页维护提示无法拦住旧客户端。
6. 在写入冻结后取第二份一致快照，处理两份快照之间的新增、修改和删除。已启用并行双写的候选库使用 `--parallel-readback`，保留已同步变更、Cloudflare 独立写入和现有登录会话。只有无法证明差量完整时才需要从冻结快照重新构建候选库。核对支付交易、退款、订单状态和时间水位，再把唯一的写入端切到 Cloudflare。重新开放前检查 Waffo 回调重投相同事件仍然只有一笔账、同步队列能继续发送，以及两个用户之间访问受限。 [增量对账](./snapshot-delta.md)
7. 回退时先冻结 Cloudflare 写入并落盘目标增量。只有在旧端还没有遗漏新订单、订阅事件和设备上传且对账通过后，才可以把流量切回旧端。如果新写入已经发生且无法对齐，应保持单写端并修复新端。

开始正式切流前，需核对域名权限、生产凭据、客户端发布状态、付费 D1 全量对账和实际负载结果。每个环境使用自己的邮件、OAuth 和账单凭据。生产流量变更按负责人指定窗口执行。

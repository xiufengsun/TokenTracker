本轮先验证真实 CLI 与本地代理，再通过真实 DOM/AX 和 SDK 验证标准 Dashboard。A 的 444 来自本机 333 加另一设备 111；C 的 555 来自本机 333 加另一设备 222。两次切换先清除账号与旧实例设备，再由真实会话登录新目标。没有注入浏览器事件、假会话或统计 props。已有 B 恢复副本、数据库卷和备份保留。

`node scripts/self-host/acceptance.cjs --plan --a http://127.0.0.1:8730 --c http://127.0.0.1:8750` 默认只输出计划。显式 `--apply` 才连接平台，要求两个不同的 loopback 目标、各自的私有服务器环境文件和仓库外专用工作目录。11 项 CLI/代理检查、两台真实远程设备和标准界面的 5 个状态均有独立记录。验收脚本不创建平台或部署函数。

完整同步使用真实解析器初始化的受控元数据 rollout，生成 canonical queue/cursors，未读取个人日志或写入 prompt/response。首次手写队列没有生产者游标，真实修复流程会重建为空；验收修正了数据初始化，没有跳过产品修复逻辑。会话重建只把应用正常 600 relay 文件中的刷新令牌读入服务端内存，经真实 SDK 验证原 UID，沿用原账号和远程设备。

最终本地队列仍为 333、1 个 bucket、1 个私有源文件，游标已消费到该文件末尾。队列内容哈希保持；正常同步会更新游标时间等元数据，因此不声明整份 cursors 文件在同步前后逐字相同。两个实例切换当下的 queue/cursors 哈希比较均通过。`test/self-host-acceptance.test.js` 的 4 项检查通过，真实页面证据另存私有验收记录，不以单元测试代替界面结果。

`init` 的首次同步子进程继承真实 `process.env`，不能为了验收配置而扫描个人日志。本轮配置验收会明确关闭这一步，并独立执行实际设备登录；不会把这个隔离步骤称为完整真实首次数据采集。
